# Slice 04 receipt — shared runtime adoption

## Changes

- Added `getContextScreenshotSetup(ctx, isActive?)` and `createContextScreenshotSetup(ctx, isActive?)` in `packages/histoire/src/node/runtime/registry.ts`. The cached helper gives one lazy setup owner to adapters sharing a development `Context`; the uncached helper gives built preview generations independent owners. Both use `createBrowserSetupPolicy(ctx.config.browser, ctx.root)`, and register owner close with Context cleanup. Development adapters pass the runtime handle's `isActive` callback, not a per-capture catalog callback.
- Threaded the development Context owner through UI capture, SDK capture, MCP screenshot and inspection, and MCP project capability reads. `launch` injection remains authoritative in preview sessions. Built preview restart creates a new owner for each generation; retirement drains the old execution lane before closing its owner.
- Passed the MCP worker's absolute root through its bootstrap tuple into `createProjectRuntimeController`, preserving selected config/root ownership when process cwd differs.
- Made MCP screenshot/inspection capability metadata refresh from current package availability and the live setup snapshot without launching a browser. A ready snapshot restores availability after a prior missing-driver result; needs-action health disables capture while test requirements continue to use their existing project/provider checks.
- Added one request-level UI setup diagnostic for structured failures, preferring the frozen `PreviewError.setup` over a later owner snapshot. Target error rows omit setup. Complete and partial results carry setup once, and complete-event validation reserves 8 KB for it while retaining 64 ordinary short-ID rows. Structured setup errors use concise fixed screenshot-browser guidance; legacy guidance remains when no setup DTO exists.

## Handoff and remaining acceptance

- Backend/UI imports can use `getContextScreenshotSetup` from `runtime/registry.ts`; it returns the Context-cached `ScreenshotSetupOwner`. For a narrower built-generation lifetime, use `createContextScreenshotSetup` and pass its own generation activity callback.
- Development package availability is only potential availability. Metadata does not launch a browser. A ready owner can recover a cached screenshot/inspection capability; `execution.available` and test-provider requirements still override that projection.
- The 8 KB diagnostic allowance is counted once per complete event. Per-target errors remain the ordinary bounded result rows.
- No real browser capture was run across UI, Node SDK, MCP HTTP and MCP stdio. Cross-entrypoint pixel/config proof and a selected existing-browser run remain open under slice 07/08. No package install, staging, commit, or push was performed.
